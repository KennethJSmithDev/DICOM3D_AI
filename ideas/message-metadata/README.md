# Synthetic interoperability message metadata prototype

This local experiment explores [DPI-I-973](https://ideas.intersystems.com/ideas/DPI-I-973): retaining useful metadata associated with messages. A separate test production sends a synthetic request with a request ID, case ID, and FHIR-style evidence reference through an IRIS service and operation. The response preserves them. The test retrieves the persisted request via IRIS `Ens.MessageHeader` and its message-body identity, and checks the session identity.

The synthetic operation rejects missing identities and returns `REVIEW_REQUESTED` for differing declared study IDs. Comparing two supplied IDs is not independent verification of either source. This is an isolated prototype. It does not modify the native AI Hub production, read patient evidence, add application permissions, provide a general metadata store, or establish authorization and retention policy. It does not claim implementation of InterSystems product features or contest acceptance. A real integration would need separately reviewed identity, data-minimization, access, retention and lifecycle contracts.

For eventual integration, the smallest candidate seam is an explicitly authorized interoperability entry adapter that wraps a native request with a separate metadata envelope and relates it to IRIS message headers and session IDs. The existing frozen `Native005.Request` contains only `Question` and `Scenario`; it has not been modified or enriched by this prototype. Correlation must not be treated as proof of patient identity, access or evidence authenticity. Configure access and retention before connecting the envelope to real records.

Run `tests/run.script` in a disposable IRIS namespace where the source files are present under `/tmp/idea973` and no other production is running. `tests/reopen.script` checks the saved synthetic message again after an owned runtime restart. The included production is only a synthetic echo; it makes no AI or FHIR calls.
